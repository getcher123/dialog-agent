# Техническое задание: Voice Agent с RAG (Deepgram + Groq + ElevenLabs + Qdrant Local)

## 1. Назначение и цели

Цель проекта: разработать тестовое веб-приложение для реал-тайм голосового бота с поддержкой RAG, двустороннего голосового диалога и целевой latency менее 800 мс для типового короткого ответа в стабильном сетевом контуре.

Базовый сценарий использования:

1. Пользователь открывает веб-страницу.
2. Нажимает `Start`.
3. Даёт доступ к микрофону.
4. Задаёт вопрос голосом на русском или английском языке.
5. Система распознаёт речь, извлекает релевантные фрагменты из документов, генерирует ответ и озвучивает его в браузере.
6. Пользователь видит транскрипт диалога, индикатор аудио и метрики задержки.

Ожидаемый результат MVP:

- браузерный full-duplex voice agent;
- RAG по загруженным PDF/DOC/текстовым документам;
- развертывание через Docker на Render/Heroku-like платформе;
- масштабирование до 10 одновременных сессий;
- измеримая телеметрия latency, WER и MOS.

## 2. Исходные ограничения

- Дата постановки задачи: март 2026.
- Целевой бюджет на API: до `$50/мес`.
- Плановый объём тестирования: `1000 минут` голосовых диалогов в месяц.
- Целевая инфраструктура деплоя: `Render`, `Heroku-like` или совместимая Docker-платформа.
- HTTPS обязателен для доступа к микрофону в браузере.

Примечание по бюджету: в исходной оценке указано `$0.06/мин x 1000 мин = $60`, что превышает целевой лимит `$50/мес`. Это противоречие должно быть закрыто на этапе реализации за счёт оптимизации пайплайна, ограничения объёма тестов либо замены части API на более дешёвые аналоги.

## 3. Область охвата

### Включено

- браузерный интерфейс для голосового диалога;
- потоковая передача аудио между браузером и backend;
- ASR через Deepgram Streaming;
- RAG-индексация пользовательских документов;
- генерация ответа через Groq Llama 3.3 70B;
- потоковый TTS через ElevenLabs;
- отображение транскрипта и метрик в UI;
- Docker-сборка и деплой;
- базовые нагрузочные и качественные тесты.

### Не включено

- полноценная CRM/админка управления пользователями;
- тонкая RBAC-модель;
- биллинг и тарификация конечных пользователей;
- production-grade multi-region отказоустойчивость;
- долговременное хранение полной истории разговоров с персональными данными.

## 4. Функциональные требования

### 4.1 Голосовой диалог

Система должна:

- поддерживать двусторонний голосовой диалог в реальном времени;
- работать в браузерах `Chrome` и `Edge`;
- использовать `getUserMedia` для захвата аудио;
- принимать поток аудио от клиента и возвращать обратно поток синтезированной речи;
- поддерживать русский и английский языки в одном приложении;
- корректно обрабатывать начало и окончание реплики пользователя через VAD;
- допускать прерывание предыдущего ответа новой репликой пользователя, если это поддержано выбранной реализацией потока.

### 4.2 RAG

Система должна поддерживать загрузку документов и ответы на вопросы по их содержимому.

Обязательные требования:

- загрузка PDF, DOC/DOCX или текстовых документов для индексации;
- разбиение документов на чанки;
- генерация эмбеддингов;
- запись эмбеддингов в локальное векторное хранилище `Qdrant`;
- retrieval по входящему текстовому запросу;
- возврат `top-3` наиболее релевантных чанков;
- передача извлечённого контекста в prompt LLM;
- выдача ответа с краткой ссылкой на использованный контекст или цитатой из документа.

### 4.3 UI

Минимальный состав интерфейса:

- кнопка `Start` для запуска сессии;
- индикатор состояния соединения;
- waveform или иной визуальный индикатор входящего/исходящего аудио;
- чат-транскрипт с репликами пользователя и ассистента;
- отображение latency-метрик;
- отображение ошибок подключения, микрофона, ASR/TTS/RAG.

### 4.4 Тестирование диалогов

Должен быть реализован тестовый контур не менее чем на `10 минут` целевых диалогов с вопросами и ответами по загруженной документации.

Нужно измерять:

- `first audio latency`;
- `end-to-end latency`;
- `WER` для распознавания;
- `MOS` или proxy-оценку качества синтеза/восприятия.

### 4.5 Деплой

Решение должно поддерживать:

- запуск через Docker;
- конфигурацию только через env vars;
- HTTPS-доступ к фронтенду;
- работу минимум с `10 concurrent` голосовыми сессиями;
- развёртывание без ручной правки кода после задания env vars.

## 5. Нефункциональные требования

### 5.1 Производительность

- целевая `first audio latency`: менее `600 мс` для `95%` запросов;
- целевая `end-to-end latency`: менее `800 мс` для коротких ответов в типовом тестовом сценарии;
- backend не должен блокировать остальные сессии при обработке одной сессии;
- обработка должна быть потоковой, без ожидания полной расшифровки и полной генерации там, где это возможно.

### 5.2 Масштабирование

- система должна выдерживать не менее `10` одновременных сессий;
- решение должно быть готово к горизонтальному масштабированию backend-инстансов;
- состояние активной сессии должно быть изолировано на уровне connection/session id.

### 5.3 Надёжность и диагностика

- все внешние API-вызовы должны логироваться в структурированном виде без утечки секретов;
- должны быть отдельные события для ASR, VAD, RAG, LLM и TTS-этапов;
- ошибки rate limit, timeout и disconnect должны обрабатываться явно;
- должны быть метрики или логи, пригодные для анализа в `Prometheus/Grafana` либо `Loki`.

## 6. Технический стек

| Компонент | Инструмент | API Key | Конфигурация |
|---|---|---|---|
| Frontend | React или Vanilla JS + `getUserMedia` | Нет | Chrome / Edge |
| Backend | Node.js + Express/ws или Python + FastAPI/WebSocket | Нет | Port `3000` |
| ASR | Deepgram Nova-3 Streaming | `DEEPGRAM_API` | `model=nova-3-general`, `interim_results=true` |
| LLM | Groq Llama 3.3 70B | `GROQ_API` | `stream=true`, `temperature=0.1` |
| RAG | Qdrant local + embeddings | Нет | `top_k=3`, context window около `4k` токенов |
| Embeddings | `text-embedding-3-small` | `OPENAI_API_KEY` или совместимый ключ провайдера эмбеддингов | `dimension=1536` |
| TTS | ElevenLabs Flash v2.5 | `ELEVENLABS_API` | `model=eleven_flash_v2_5`, `stream=true`, `voice=ru_voice` |
| VAD | Silero VAD | Нет | `threshold=0.5`, `chunk=30ms` |
| Deploy | Docker + Render/Heroku-like | Нет | env-based config |

Примечание: если для эмбеддингов используется `text-embedding-3-small`, в проекте требуется отдельный ключ провайдера эмбеддингов. Это должно быть отражено в `.env.example` и в инструкции по запуску.

## 7. Архитектура и поток обработки

Базовый поток:

```text
Browser UI
  <-> WebSocket / streaming transport
Backend session handler
  <- audio chunks (16 kHz mono)
  -> Deepgram Streaming ASR
  -> VAD / end-of-utterance detection
  -> embeddings(query)
  -> Qdrant top-3 retrieval
  -> Groq LLM streaming completion
  -> ElevenLabs streaming TTS
  -> audio chunks back to browser
```

Целевой пайплайн обработки реплики:

1. Браузер отправляет аудиочанки на backend.
2. Backend стримит аудио в Deepgram.
3. Deepgram отдаёт interim/final text.
4. После детекции конца фразы backend инициирует RAG-запрос.
5. Из пользовательского текста строится embedding.
6. Qdrant возвращает `top-3` чанка.
7. Backend формирует prompt: системные инструкции + вопрос пользователя + RAG-контекст.
8. Groq стримит ответ токенами.
9. Ответ или его части отправляются в ElevenLabs.
10. Браузер получает аудиопоток и воспроизводит его.
11. UI параллельно показывает транскрипт и latency-метрики.

## 8. Требования к данным и индексации

### 8.1 Загружаемые данные

Поддерживаемые типы документов:

- `.pdf`
- `.doc`
- `.docx`
- `.txt`
- `.md`

### 8.2 Индексация

На этапе инициализации RAG должны быть реализованы:

- загрузка файла пользователем или из локального каталога;
- извлечение текста;
- очистка служебного мусора;
- чанкинг документа;
- генерация эмбеддингов;
- upsert в Qdrant с метаданными.

Минимальный состав метаданных чанка:

- `document_id`
- `document_name`
- `chunk_id`
- `page` или логический раздел, если доступен
- `source`

### 8.3 Retrieval

При запросе пользователя:

- выполняется embedding только текстовой части запроса;
- retrieval ограничен `top-3`;
- в prompt передаются только чанки, прошедшие порог релевантности, если он реализован;
- если релевантный контекст не найден, ассистент должен явно сообщить, что в документах не найден подтверждённый ответ.

## 9. Требования к интерфейсу

Страница MVP должна содержать:

1. Заголовок приложения.

## 12. Тестирование и метрики

### 12.1 Обязательные тесты

- не менее `10 минут` голосовых диалогов;
- Q&A по загруженным документам;
- проверка русского и английского сценариев;
- проверка ответа на вопрос вида `Расскажи о [тема из PDF]`;
- проверка отсутствия hallucination при отсутствии релевантного контекста.

### 12.2 Метрики

| Метрика | Определение | Цель |
|---|---|---|
| First audio latency | От конца пользовательской фразы до первого аудиочанка ответа | `< 600 мс` p95 |
| End-to-end latency | От конца пользовательской фразы до окончания возврата аудиоответа | `< 800 мс` для коротких ответов |
| WER | Ошибка распознавания речи по тестовому набору | Минимизировать, измерять на контрольных фразах |
| MOS | Субъективная оценка качества синтеза | Не ниже целевого порога, согласованного на тестах |

### 12.3 Логирование и наблюдаемость

Минимум должны собираться:

- timestamps по каждому этапу пайплайна;
- session id;
- длительность ASR, retrieval, LLM и TTS;
- количество retrieved chunks;
- ошибки и retry-события.

Целевые инструменты:

- `console.log` на MVP-этапе;
- `Loki` для логов;
- `Prometheus/Grafana` для метрик latency, WER и общей диагностики.

## 14. Критерии приёмки

Решение считается принятым, если выполнены все условия ниже:

1. Пользователь может начать голосовой диалог из браузера без локальной установки дополнительного ПО.
2. Система корректно принимает голос, распознаёт речь и отвечает синтезированным голосом.
3. Для вопроса по загруженному PDF система отвечает по содержимому документа и показывает цитату либо ссылку на источник.
4. `First audio latency` не превышает `600 мс` для `95%` тестовых обращений.
5. Средняя стоимость эксплуатации не превышает целевой лимит либо согласовано отклонение от него.
6. Приложение разворачивается через Docker с настройкой только через env vars.
7. Наблюдаемость позволяет анализировать latency, WER и ошибки пайплайна.

## 15. Риски и резервные решения

| Риск | Последствие | Решение |
|---|---|---|
| API rate limits | Рост ошибок и времени ответа | Retry logic, очередь, backoff |
| Latency spikes | Нарушение SLA по voice UX | Региональные endpoint'ы, профилирование этапов |
| Недоступность ElevenLabs | Нет голосового ответа | Fallback на локальный или альтернативный TTS |
| Сбой локального Qdrant | Ошибки индексации или retrieval | Перезапуск локального контейнера/процесса и восстановление коллекции |
| Превышение бюджета | Выход за лимит `$50/мес` | Сокращение минут, оптимизация TTS/ASR, замена части стека |
| WebSocket-ограничения хостинга | Нестабильная работа real-time пайплайна | Выбор платформы с гарантированной поддержкой long-lived connections |
